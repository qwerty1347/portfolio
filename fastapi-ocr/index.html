→ Multi-engine OCR API · Sync & Async dual mode · Celery-backed job pipeline

EasyOCR · PaddleOCR · Naver Clova OCR을 단일 인터페이스로 추상화하여 추가 확장이 용이한 구조로 설계했습니다
무거운 추론은 Celery 워커로 분리해 API 응답 지연을 방지하고 비동기 처리 구조를 구현했습니다.
ocr_jobs 테이블이 pending → started → success/failed 라이프사이클을 관리하며 안정적인 처리 흐름을 구현했습니다.

01 // overview

Celery 워커를 사용한 이유

sync
POST /api/v1/ocr/

가벼운 단일 이미지. 요청 → 추론 → 응답이 한 번에 이뤄지는 단순 경로. asyncio.to_thread로 추론을 별도 스레드에 위임해 이벤트 루프 블로킹을 차단합니다.

vs
async
POST /api/v1/ocr/jobs

대용량/PDF/배치 워크로드. 즉시 job_id 발급 후 Celery 워커가 백그라운드 처리. 클라이언트는 GET /jobs/{id}로 폴링. acks_late·reject_on_worker_lost로 워커 장애에도 안전합니다.

04 // highlights

기술적 의사결정

001

OCR 엔진 추상화 + Lazy 팩토리

BaseEngine ABC가 recognize(file_path: Path) → dict 한 가지 시그니처로 통일. OcrModule._FACTORIES가 첫 호출 시점에만 모델을 메모리로 올려, 사용하지 않는 엔진은 워커 RSS에서 제외됩니다. 새 엔진 추가는 클래스 1개 + 팩토리 dict에 1줄.

ABC lazy init memory
002

이중 DB 세션 — async/sync 공존

FastAPI는 aiomysql 기반 AsyncSession을, Celery 워커와 Alembic은 pymysql 기반 Session을 같은 MySQL에 병존시킵니다. 컨텍스트별 최적 드라이버를 선택하되, pool_pre_ping·pool_recycle로 wait_timeout 끊김을 자동 회복.

aiomysql pymysql pool
003

잡 라이프사이클 + 멱등성

ocr_jobs 테이블에 상태 전이를 영속화. STARTED는 즉시 commit해 외부 가시성을 확보하고, 추론 부분만 try/except로 감싸 SUCCESS/FAILED를 분기 commit한 뒤 raise로 Celery에 결과를 정확히 전달합니다. 같은 job_id로 재실행되어도 같은 row를 갱신만 하므로 acks_late + reject_on_worker_lost와 정합.

idempotent acks_late retry-safe
004

이벤트 루프 보호 — to_thread

EasyOCR/PaddleOCR은 본질적으로 동기·CPU bound 추론입니다. async 엔드포인트에서 그대로 호출하면 FastAPI 이벤트 루프 전체가 멈춥니다. asyncio.to_thread(engine.recognize, path)로 별도 스레드에 위임해 동시 요청 처리 능력을 유지합니다.

asyncio CPU bound
005

큐/워커 정책 튜닝

worker_prefetch_multiplier=1로 무거운 추론의 선점 분산, task_acks_late=True로 워커 장애 시 broker 재할당, worker_max_tasks_per_child=200으로 OCR 모델 메모리 누수 방지, task_time_limit=5min·soft_time_limit=4min으로 멈춘 잡의 워커 점유 차단.

prefetch soft-limit memory-leak
006

전역 예외 → 통일된 응답 봉투

HTTPException·RequestValidationError·JWTError·BusinessException· 그 외 모든 Exception이 {code, message, errors[]} 봉투로 정규화됩니다. 라우터/서비스 레이어는 비즈니스 예외만 던지면 끝.

global handler consistency
