멀티 엔진 OCR_

OCR 엔진을 인터페이스로 추상화하여 추가 확장이 용이한 구조로 설계했습니다. 무거운 추론은 Celery 워커로 분리해 비동기로 구현하여 API 응답 지연을 방지하였습니다. pending → started → success/failed 라이프사이클을 관리하며 안정적인 처리 흐름을 구현하였습니다.

02 overview

동기 / 비동기 두 가지 처리 흐름

단발성 가벼운 요청은 POST /ocr/ 로 즉시 응답하고, 무거운 추론·배치는 POST /ocr/jobs 로 잡을 등록해 Celery 워커가 백그라운드 처리합니다. 응답성과 처리량을 양립시키기 위한 분리입니다.

동기 OCR 흐름 · POST /api/v1/ocr/

[Client]                [FastAPI]                [OCR Engine]
   │                       │                          │
   │ POST /api/v1/ocr/     │                          │
   │ (file, engine)        │                          │
   ├──────────────────────►│                          │
   │                       │ JWT verify               │
   │                       │ file validate            │
   │                       │ save temp                │
   │                       │                          │
   │                       │ asyncio.to_thread()      │
   │                       ├─────────────────────────►│
   │                       │   engine.recognize()     │
   │                       │   → result               │
   │                       │◄─────────────────────────┤
   │                       │ delete temp              │
   │                       │                          │
   │ { code, data:{images}}│                          │
   │◄──────────────────────┤                          │

EasyOCR · PaddleOCR 은 sync · CPU bound. async 라우터에서 직접 호출하면 이벤트 루프가 멈추므로 asyncio.to_thread() 로 워커 스레드에 위임해 동시 요청 처리 능력을 유지합니다.

비동기 잡 흐름 · POST /api/v1/ocr/jobs

[Client]            [API]               [MySQL]            [Redis]            [Worker]
   │ POST /jobs       │                    │                  │                  │
   ├─────────────────►│                    │                  │                  │
   │                  │ INSERT pending     │                  │                  │
   │                  ├───────────────────►│                  │                  │
   │                  │ enqueue run_ocr    │                  │                  │
   │                  ├──────────────────────────────────────►│                  │
   │ 202 {job_id}     │                    │                  │ pull             │
   │◄─────────────────┤                    │                  ├─────────────────►│
   │                  │                    │ UPDATE started   │                  │
   │                  │                    │◄─────────────────────────────────── │
   │                  │                    │                  │  do OCR (3~30s)  │
   │                  │                    │ UPDATE success   │                  │
   │                  │                    │◄─────────────────────────────────── │
   │ GET /jobs/{id}   │                    │                  │                  │
   ├─────────────────►│ SELECT             │                  │                  │
   │                  ├───────────────────►│                  │                  │
   │ {status, result} │                    │                  │                  │
   │◄─────────────────┤                    │                  │                  │

STARTED 즉시 commit 으로 외부 가시성 확보 → 추론 → SUCCESS/FAILED 분기 commit. 같은 job_id 로 재실행되어도 같은 row 를 갱신만 하므로 acks_late + reject_on_worker_lost 와 정합합니다.

03 highlights

기술적 결정

001

celery 워커 비동기 처리

EasyOCR · PaddleOCR · Clova OCR 은 한 장당 3~30초가 걸리는 무거운 추론. 동기 라우터에서 직접 호출하면 워커 프로세스가 그 시간만큼 점유되어 동시 요청 처리량이 떨어집니다. POST /ocr/jobs 로 잡을 등록하면 즉시 job_id 를 반환하고 실제 추론은 Celery 워커가 백그라운드에서 처리. 무거운 추론에 맞춰 worker_prefetch_multiplier=1 로 잡이 한 워커에 몰리지 않게 분배하고, worker_max_tasks_per_child=200 으로 모델 메모리 누수를 방어합니다.

celery redis prefetch=1 background job
002

잡 라이프사이클 + 멱등성

ocr_jobs 테이블에 상태 전이를 영속화. STARTED는 즉시 commit해 외부 가시성을 확보하고, 추론 부분만 try/except로 감싸 SUCCESS/FAILED를 분기 commit한 뒤 raise로 Celery에 결과를 정확히 전달합니다. 같은 job_id로 재실행되어도 같은 row를 갱신만 하므로 acks_late + reject_on_worker_lost와 정합.

idempotent acks_late retry-safe
003

OCR 엔진 모듈화

세 엔진(EasyOCR · PaddleOCR · Clova OCR)을 BaseEngine ABC 로 통합해 recognize(file_path) + convert_to_json(raw) 시그니처를 강제했습니다. 라우터·워커는 엔진별 구현을 알 필요 없이 추상 인터페이스만 호출하면 되고, 신규 엔진 추가는 app/module/ocr/ 에 클래스 1개 작성 + OcrModule.OCR_ENGINES 딕셔너리에 한 줄 등록으로 끝납니다. 결과 JSON 도 통일되어 클라이언트 입장에서 엔진 교체가 무비용.

ABC strategy pattern open/closed
