멀티 엔진 OCR_

OCR 엔진을 인터페이스로 추상화하여 추가 확장이 용이한 구조로 설계했습니다. 무거운 추론은 Celery 워커로 분리해 비동기로 구현하여 API 응답 지연을 방지하였습니다. pending → started → success/failed 라이프사이클을 관리하며 안정적인 처리 흐름을 구현하였습니다.

01 overview

Celery 워커 비동기로 구현한 이유

async
POST /api/v1/ocr/jobs

대용량/PDF/배치 워크로드. 즉시 job_id 발급 후 Celery 워커가 백그라운드 처리. 클라이언트는 GET /jobs/{id}로 폴링. acks_late·reject_on_worker_lost로 워커 장애에도 안전합니다.

잡 라이프사이클 + 멱등성

ocr_jobs 테이블에 상태 전이를 영속화. STARTED는 즉시 commit해 외부 가시성을 확보하고, 추론 부분만 try/except로 감싸 SUCCESS/FAILED를 분기 commit한 뒤 raise로 Celery에 결과를 정확히 전달합니다. 같은 job_id로 재실행되어도 같은 row를 갱신만 하므로 acks_late + reject_on_worker_lost와 정합.

idempotent acks_late retry-safe
