레거시 리팩토링 하네스_

레거시 코드를 정리해 주는 Claude Code 자동화 도구입니다. 파일 하나를 지정하면 AI 에이전트 네 개가 순서대로 붙어서 진단하고, 계획을 세우고, 코드를 고치고, 마지막에 검토까지 합니다. 대신 하는 일을 많이 줄였습니다. 코드를 옮기고 구조를 바꾸는 것까지만 하고, 동작이 달라질 수 있는 수정은 손대지 않습니다. 원본 파일도 건드리지 않습니다. 결과물은 따로 쌓이고, 실제로 반영할지는 diff 를 보고 직접 정합니다.

01 architecture

에이전트 파이프라인

명령어 한 번이면 검토까지 갑니다. 중간에 확인을 받지 않습니다. 멈추는 건 파일을 못 찾았을 때랑 작업 하나가 실패했을 때, 두 경우뿐입니다. 

   /refactor {대상 파일}
        │
        ▼
   refactor  ─ 스킬 · 오케스트레이터
        │        0 이어하기 판정 → 1 대상 확정 → 2 스택·파일 종류 판정
        │        3 근거·런타임 제약 수집 → 4 00_input.md 작성
        ▼        → _workspace/00_input.md   기준 정리 · 언어와 버전 · 참고할 설정 파일
   legacy-analyzer                                      Read · Grep · Write
        │        읽는 것 — 대상 파일 · 00 · 근거로 지정된 설정 파일
        ▼        → 01_legacy_analysis.md   진단 · 무엇이 문제이고 몇 번째 줄인지
   refactoring-strategist                               Read · Write
        │        읽는 것 — 00 · 01 만. 대상 파일도 열지 않는다
        ▼        → 02_refactoring_strategy.md   계획 · 할 것과 이번엔 안 할 것
   refactoring-engineer                                 Read · Write
        │        작업 하나당 한 번씩 반복 호출 · 결과물이 output/ 에 누적
        ▼        → 03_migration_plan.md · _workspace/output/{원본 경로}
   modernization-reviewer                               Read · Grep · Write
        │        읽는 것 — _workspace/ 산출물 전부 (output/ 결과물 포함)
        ▼        → 04_review_report.md   검토 · 어긋난 곳과 확인할 것
   사용자
                 diff -r app/ _workspace/output/app/   →   복사는 사람이 한다

고치지 말라고 프롬프트에 아무리 적어도 지켜지지 않을 때가 있습니다. 그래서 도구를 뺐습니다. 네 에이전트 모두 Edit 이 없어서 기존 파일을 수정하지 못하고, Glob 이 없어서 지정한 파일 밖으로 못 나갑니다. 결과물이 _workspace/output/ 에만 쌓이는 건 그 때문입니다. analyzer 한테만 Grep 을 줬는데, 이것도 대상 파일 경로를 고정해서 넘깁니다.

02 overview

코드를 옮기는 것까지만 합니다

메서드로 빼내고, 파일을 나누고, 흩어진 중복을 한군데로 모읍니다. 딱 여기까지입니다. 조건문을 고치거나 예외 처리를 새로 넣는 건 하지 않습니다. 빠진 것처럼 보이는 검사도 추가하지 않습니다. 그 순간부터는 코드 정리가 아니라 기능 수정인데, 테스트가 없는 레거시에서 기능 수정은 대체로 사고로 이어집니다.

이상해 보이는 코드에도 대개 이유가 있습니다. 문제는 그 이유가 파일 안에 안 적혀 있다는 거라서, 왜 이렇게 짰는지 모르겠는 코드는 그냥 둡니다.

빼내는 기준도 정해뒀습니다. 같은 코드가 두 군데 이상 나오고, 여러 줄이 한 덩어리로 움직일 때만 빼냅니다. 한 줄짜리를 함수로 감싸는 건 안 합니다.

작업하면 생기는 파일 · _workspace/

   _workspace/
   ├── 00_input.md                  어떤 파일을, 어떤 언어·버전 기준으로 볼지
   ├── 01_legacy_analysis.md        진단 — 무엇이 문제이고 몇 번째 줄에 있는지
   ├── 02_refactoring_strategy.md   계획 — 무엇부터 할지, 이번에 안 할 것은 무엇인지
   ├── 03_migration_plan.md         실행 기록 — 작업마다 무엇을 옮겼는지
   ├── 04_review_report.md          검토 — 계획과 어긋난 곳, 적용 전에 돌려볼 것
   └── output/                      정리된 코드 (원래 폴더 구조 그대로)

작업이 끝나면 _workspace 폴더 하나가 생기고 원래 파일은 그대로입니다. 결과물 경로에서 _workspace/output/ 만 떼면 원래 위치와 같아서, diff 로 바로 비교됩니다.

03 highlights

기술적 결정

진단 · 계획 · 실행 · 검토를 각각 다른 에이전트가 맡습니다. 아래 세 가지는 처음부터 정해둔 게 아니라, 만들면서 문제가 생겨서 넣은 규칙입니다.

001

세어 보게 만들기

진단 리포트에 이 코드가 아홉 군데 있다고 적어놓고 정작 여섯 군데만 설명하는 일이 있었습니다. 같은 파일에서 다섯 번 연속 그랬습니다. 설명이 안 붙은 세 군데는 정리할 때도 그대로 빠집니다.

그래서 위치를 적을 때 검색으로 개수를 세고, 리포트에 인용한 개수와 맞는지 확인하는 절차를 넣었습니다. 눈으로 세면 꼭 틀립니다.

직접 세어 보기 빠진 곳 찾기
002

확인 못 한 건 확인 못 했다고 쓰기

검사할 방법이 없는 항목은 확인 못 함이라고 적습니다. 문제 0건이라고 쓰지 않습니다. 0건은 검사해서 통과했다는 뜻으로 읽히니까요. 틀린 지적은 다시 보면 되지만, 검사도 안 하고 통과라고 적어둔 건 아무도 다시 안 봅니다.

확인 못 함 통과 착각 막기
003

요약 대신 원본 넘기기

처음에는 단계마다 앞 단계 결과를 요약해서 넘겼습니다. 그랬더니 몇 번째 줄인지 같은 정보가 제일 먼저 사라지고, 요약을 한 번 더 거치면 원문에 없던 얘기까지 나왔습니다. 지금은 요약을 아예 안 넘깁니다. 어떤 파일을 읽을지만 알려주고 나머지는 각자 읽습니다.
