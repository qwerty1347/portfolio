개발 노트 RAG 챗봇_

직접 정리한 개발 노트를 gemini-embedding-001 로 임베딩해 Pinecone 에 적재하고, 질문하면 Gemini 가 그 기록만 근거로 답하는 서버리스 RAG 채팅입니다. 문서 소스는 GitHub repo · 로컬 폴더 · Google Drive 중 택일·병행이 가능하고, 채팅 API 는 Vercel 서버리스 함수로 배포해 상시 구동 서버 없이 운영합니다. 바이브 코딩으로 만든 프로젝트라, 생성된 코드를 그대로 두지 않고 무료 티어 쿼터 · 모델 EOL · 유사도 점수 분포를 직접 실측해 검증한 과정을 함께 정리했습니다.

02 overview

쓰기와 읽기의 분리 · index → search → answer

인덱싱(쓰기)과 채팅(읽기)을 완전히 분리했습니다. 인덱싱은 노트가 늘었을 때만 로컬에서 수동으로 돌리는 일회성 배치이고, 서버리스 함수로 배포되는 것은 채팅 경로뿐입니다. 덕분에 상시 구동 서버 없이도 무거운 임베딩 작업이 사용자 요청 경로에 얹히지 않습니다.

인덱싱 · npm run index:github (로컬 수동 실행)

   GitHub repo ─┐
   로컬 폴더   ─┼─► 문서 수집 (.md / .txt)
   Google Drive ┘        │
                         ▼
                  manifest 대조
                         │        .indexed-github.json 에 기록된 파일은 skip → 증분 인덱싱
                         ▼
                  chunkText(size=1000, overlap=150)
                         │        청크 경계에 걸친 내용도 잡히도록 150자 오버랩
                         ▼
                  embed(chunk, "RETRIEVAL_DOCUMENT")
                         │        gemini-embedding-001 · 768차원 · L2 수동 정규화
                         ▼
                  vectorId = "gh:" + sha1(path) + ":" + i
                         │        한글 경로 → 결정적 ASCII ID (재실행 시 덮어쓰기)
                         ▼
                  Pinecone upsert
                                  100개 배치 · 파일 1개 끝날 때마다 manifest 저장
                                  → 중간에 끊겨도 다시 돌리면 이어서 진행

Pinecone 벡터 ID 는 ASCII 만 허용해서 한글 파일명이 그대로 들어가지 못합니다. sha1(path) 로 결정적 ID 를 만들어, 같은 파일을 다시 인덱싱하면 새 벡터가 쌓이는 대신 기존 벡터를 덮어쓰도록 했습니다. 임베딩은 3072차원을 768로 줄여 받기 때문에 단위벡터가 아니라, 코사인 유사도가 정확히 동작하도록 직접 L2 정규화합니다.

채팅 · POST /api/chat (Vercel 서버리스 함수)

   브라우저
      │  ① 질문
      ▼
   route.ts
      │  ② embed(question, "RETRIEVAL_QUERY")
      │        저장은 DOCUMENT, 검색은 QUERY 로 task type 을 나눠 검색 품질 확보
      ▼
   Pinecone query(topK=5, includeMetadata)
      │  ③ 관련 청크 + fileName + score
      ▼
   chat(question, context)
      │        gemini-3.5-flash-lite 로 먼저 시도
      │        ↪ 429 / 500 / 503 → withRetry 2·4·8·16s 지수 백오프 (최대 5회)
      │        ↪ 그래도 실패 → gemini-3.5-flash → gemini-3.6-flash 로 폴백
      ▼
   답변(GFM 마크다운) + 출처 링크
      │        react-markdown + remark-gfm 로 표·코드펜스 렌더링
      │        rehype-raw 는 의도적으로 미사용 → 노트 속 HTML 은 이스케이프 (XSS 차단)
      ▼
   브라우저

프롬프트에서 «자료에 없는 내용은 추측하지 말고 모른다고 답하라» 를 명시해 환각을 억제하고, 답변과 함께 근거가 된 노트를 출처 링크로 함께 내려 사용자가 직접 원문을 확인할 수 있게 했습니다. 예외는 route.ts 에서 사용자용 문구로 치환하고, 원문은 개발 환경에서만 detail 필드로 내려보냅니다.

03 highlights

기술적 의사결정

001

모델별 쿼터를 이용한 폴백 체인

무료 티어 429 응답을 뜯어보니 쿼터 ID 가 GenerateRequestsPerDayPerProjectPerModel — 즉 모델별로 따로 잡힙니다. 한 모델이 하루 20회를 소진해도 다른 모델은 살아 있다는 뜻이라, CHAT_MODELS 배열(3.5-flash-lite → 3.5-flash → 3.6-flash)을 순차 시도하는 폴백 체인을 넣어 채팅 상한을 20회에서 약 60회로 늘렸습니다. 일시적 혼잡(503)은 그 앞단의 withRetry 지수 백오프가 흡수합니다.

quota fallback chain exponential backoff
002

클라이언트 지연 초기화

Pinecone · Gemini 클라이언트를 모듈 최상단에서 만들면 next build 의 page data 수집 단계에서 환경변수가 없어 생성자가 터집니다. 실제 사용 시점에 만들도록 지연 초기화로 바꿔 빌드 실패를 없앴습니다. 대신 PINECONE_INDEX 에는 기본값 폴백을 두지 않았습니다 — 폴백이 있으면 Vercel 에 변수를 빠뜨렸을 때 존재하지 않는 인덱스를 조용히 바라보게 되므로, 즉시 던지는 편이 안전합니다.

lazy init build time fail fast
003

한글 경로 → 결정적 ASCII 벡터 ID

Pinecone 벡터 ID 는 ASCII 만 허용하는데 노트 파일명은 대부분 한글입니다. vectorId(prefix, path, i) = prefix:sha1(path):i 로 해싱해 같은 경로 + 같은 청크 번호는 항상 같은 ID 가 되도록 했습니다. 재인덱싱해도 중복이 쌓이지 않고 덮어쓰기됩니다.

sha1 idempotent upsert
004

매니페스트 기반 증분 인덱싱

무료 티어에서 수십 개 문서를 임베딩하면 중간에 429 로 끊기기 쉽습니다. 파일 1개를 upsert 할 때마다 .indexed-github.json 에 진행 상황을 기록하고, 다음 실행에서 그 목록을 건너뜁니다. 끊겨도 다시 돌리면 이어서 진행되고, 노트가 늘었을 때도 새 파일만 자동으로 감지합니다.

manifest resumable incremental
005

GitHub API 호출 최소화

문서를 GitHub API 로 하나씩 받으면 rate limit 에 바로 걸립니다. API 는 기본 브랜치 조회 + 트리 조회 2회만 쓰고, 실제 파일 원문은 rate limit 이 적용되지 않는 raw.githubusercontent.com CDN 에서 받아옵니다. 공개 repo 라 인증도 불필요합니다.

rate limit CDN
006

에러 노출 이원화

Google 원문 JSON 이 사용자 화면에 그대로 뜨지 않도록 RESOURCE_EXHAUSTED|UNAVAILABLE|429|503 패턴을 «지금 AI 서버가 혼잡하거나 무료 사용량을 초과했습니다» 로 치환합니다. 대신 NODE_ENV !== "production" 일 때만 원문을 detail 필드로 함께 내려 터미널을 안 봐도 채팅 화면에서 500 의 원인이 바로 보이게 했습니다.

error handling DX
04 workflow

작업 방식 · 바이브 코딩으로 만들고, 실측으로 검증하기

평소 다루던 Python · PHP 백엔드가 아닌 Next.js · TypeScript 스택을, 기획부터 배포까지 AI 페어 프로그래밍(바이브 코딩)으로 구축했습니다. 다만 «돌아가니까 됐다» 로 끝내지 않고, LLM 을 쓰는 서비스에서 실제로 굴려봐야 드러나는 것들을 직접 측정해 근거를 남기는 데 시간을 더 썼습니다.

직접

실측으로 확인한 것들

모델 가용성 — ListModels 응답에 이름이 보여도 쓸 수 있다는 뜻이 아닙니다. gemini-2.5-flash 는 목록에는 그대로 나오면서 generateContent 만 404 를 냅니다. 반드시 실제 호출로 확인해야 한다는 걸 겪고, 모델 목록을 폴백 체인으로 재구성했습니다.

모델별 응답 속도 — 5회 호출 실측: 3.5-flash-lite 5초 / 3.5-flash 8초 / 3.6-flash 10초 / 3.1-flash-lite 55초. 폴백 체인의 순서는 이 측정값으로 정했습니다.

유사도 점수 분포 — 관련 질문은 0.64~0.77, 완전히 무관한 질문("오늘 서울 날씨")도 0.51~0.53 이 나옵니다. gemini-embedding-001 은 점수 범위가 압축돼 있어 0% 가 아니라 50% 부근이 기준선이라는 것, 그래서 퍼센트 표기가 오해를 부르는 지표라는 것을 수치로 확인했습니다.
